# ARCHITECTURE.md：專案結構地圖（選配）

先遵守 SKILL.md 的共通規則。ARCHITECTURE 回答「這個專案由哪幾塊組成、要改某處會牽動什麼」，讀者是要改程式的人；怎麼安裝、怎麼使用留在 [README](readme.md)。判準：照著做就能用的寫 README；改程式之前才需要知道的寫這裡。

## 何時寫、放在哪裡

- 主人說「更新架構文件」或指名 ARCHITECTURE 時寫。它不屬任何分組，「更新文件」也不含它。主機若設有架構掛勾，掛勾提示時也可以寫，範圍只限下方〈掛勾觸發〉。
- 只有專案根目錄的 `ARCHITECTURE.md`（或主人指定的檔）算數。既有的架構筆記、永久知識庫的副本、規範附檔都不算同用途檔：只連過去，不改它們，也不自動把內容搬進來；要搬由主人指示。
- 規範附檔＝某專案 AGENTS.md 明文指定、隨程式改動維護的規則檔；何時更新照該專案 AGENTS.md，不歸本規格管。
- 平常改程式前可以讀，用來找該動哪裡。落後不提醒（見 SKILL.md）。

## 檔頭必填

- 專案／工作主題、最後更新時間。
- 內容確認截至：實際時間與確認範圍；未確認的部分明說。
- Git 基準：全文重查時對照的程式版本（完整 commit）。只在主人說「更新架構文件」、全文重查後推進。
- 掛勾核對到（選填，主機設有架構掛勾時）：掛勾最後一次核對的完整 commit，只代表訊號涉及的部分。掛勾以它為起算點，沒有就用 Git 基準；全文重查時跟 Git 基準一起推進。
- 確認當下的工作目錄狀態：clean／dirty／unknown，依 [有效性核對](freshness.md)。

## 寫入門檻

只寫 **Git 基準裡已提交的現行結構**。規劃中、別的分支上、還沒提交的不寫；試驗中的做法標明「試驗中」或不寫。

## 內容

不適用的段落省略，不留空白標題。

1. **總覽**：一段話說明專案做什麼、由幾塊組成。
2. **元件地圖**：每塊的名稱、職責、位置（目錄、服務或機器）。路徑寫成反引號包住的相對路徑，例如 `src/api/`，方便搜尋與檢查；不寫行號。
3. **資料流與接口**：資料從哪裡進、經過哪些元件、從哪裡出；元件之間靠什麼溝通（API、檔案、佇列、資料表）。
4. **不能打破的邊界**：例如某元件只吃另一元件交出的固定格式。已寫在 AGENTS.md 或規範附檔的規則只連過去，不重寫一份。
5. **為什麼這樣切**：一兩句原因；演變與決策細節連到 status 的決策紀錄或永久知識庫，不抄。

不寫：安裝與操作步驟（README）、逐檔說明、行號、進度與驗證結果（status）、待辦（todo）、AI 的工作規則（AGENTS.md）。

## 更新

- 主人說「更新架構文件」時，重查既有敘述是否仍符合現行程式：過時的改掉，重查過的才更新內容確認時間。不存在且有符合門檻的內容才建立；沒有就回報「尚無符合門檻的內容，未建立」。
- 寫入前重讀原檔，保留有效內容與其他人的工作（共通規則 3）。
- 寫文件不代表提交；提交照各專案原本的流程與主人指令。

## 掛勾觸發

- 只改 ARCHITECTURE.md 受影響的段落，把「掛勾核對到」寫成掛勾給的 commit；Git 基準與內容確認時間不動。判斷不必改時只更新「掛勾核對到」。
- 不改其他文件、不提交、不問主人、不提醒；完成後回報一句改了哪裡。這份改動留在工作目錄，下一次照原流程提交時一併帶上。
- 掛勾的訊號只看檔案結構，是下限：資料流、認證方式或接口改了但目錄沒變時不會觸發。不能把「掛勾沒提示」當成「架構沒變」；主人說「更新架構文件」時一律重查。
- 這是「只有主人要求才寫」的唯一例外，只限 ARCHITECTURE.md，不類推到 README、status 或其他文件。
