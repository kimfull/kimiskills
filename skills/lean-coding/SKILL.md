# Lean Coding｜輕量開發

在理解相關行為、完成必要驗證的前提下，用最低的整體成本完成當前需求。整體成本包含修改、驗證、排障與日後維護，所以「輕量」不是壓縮行數，更不是省略安全。

專案指令與使用者當下的要求優先於本 Skill；專案流程較嚴格時照專案走，不拿「輕量」當降級理由。本 Skill 不擴大任何工具權限或授權。

## 先分級：風險決定做多少

依失敗後果與影響範圍分級，不看行數、檔案數、檔案類型或「小修」這個名稱：一行樣式若影響權限呈現或提交行為就不是低風險，共用邏輯、資料與環境設定的變動至少算一般。在腦中分級即可，不必寫風險報告。

| 層級 | 典型範圍 | 動手前 | 最低驗證 |
| --- | --- | --- | --- |
| 低 | 文字、樣式、局部且可逆的小修 | 需求明確就直接做，不必寫計畫 | 相關預覽、檢查或既有測試 |
| 一般 | 一般邏輯、API、局部重構 | 各一句：要達成什麼、改哪裡、怎麼驗證 | 主要成功結果、不可破壞的條件、最重要的失敗反例；受影響的既有測試與必要的型別／建置檢查 |
| 高 | 權限、租戶隔離、付款計費、資料遷移、並行狀態、外部副作用、公開契約、不可逆操作 | 同上；關鍵歧義先問 | 同上，再依風險加拒絕、重複、重試、中途失敗與資料保護；區分「確定失敗」與「結果未知」；驗證可行的復原方式 |

## 1. 先看現況

- 先讀適用的專案指令、相關程式、套件 scripts、設定與測試；小修不必遍讀全庫。
- 確認既有變更；使用者未提交的工作不覆蓋、不 reset。
- 版本、支援狀態、API、限制、計價不確定時查當前官方文件，不憑記憶寫數值；查不到就明說，不據此做不可逆操作。
- 涉及 Cloudflare Workers 的後端或設定時，先讀 Workers 參考（條件見文末）。

## 2. 釐清需求：先查，再自己決定，最後才問

- 行為變更先確認可觀察的成功結果與不可破壞的條件。驗收依據來自需求、既有契約或缺陷重現；從新實作的輸出反推預期，只能證明程式做了它做的事。簡單任務不硬湊案例或文件。
- 已知的不重問；資訊不足先查程式與設定。
- 低風險、可逆的實作選擇自己決定，簡述必要假設。
- 業務規則不是技術細節，沒確認就不猜。影響權限、租戶資料、計費、公開契約或不可逆行為的關鍵歧義，集中一次問完。
- 未解決的高風險歧義只擋相關步驟，其餘安全的部分繼續。
- 使用者只要分析或計畫時，不動手修改。
- 較大的功能拆成可端到端驗證的小段，做完一段再擴展；切點看能否獨立驗證，不看固定分鐘數或 Token 數。

## 3. 架構按需求長

每一層抽象、每個依賴與服務，之後每次修改與排障都要再付一次成本，所以等需求出現再加。

- 既有專案沿用現有語言、框架、目錄與套件管理器；先查既有實作，再比較標準函式庫、平台功能與已安裝套件，以需求、相容性及整體成本選擇，不固定排名。「更輕量」不是全案重寫或拆掉既有抽象的理由。
- 新模組從清楚的函式、資料型別與直接呼叫開始，不預設 Controller → Service → Repository 分層、DI 容器、事件匯流排、插件系統或微服務。
- 拆分能明顯改善閱讀、測試或安全邊界，或已有實際重複／第二種實作時，才抽模組或介面；不必湊滿固定重複次數，也不要塞成一個巨型檔案。
- 彈性留在會變動的邊界（第三方 API、儲存、模型供應者），用小函式隔離；確認需要多供應者才定義最小共同介面，不預建通用 Adapter／Factory。
- 新增依賴、層級或服務（含資料庫、快取、Queue、背景排程、空目錄）前，用一句話說出「解決哪個當前問題、現有方式為何不足」，說不清楚就不加。
- 但認證、加密這類高風險功能用成熟套件，不為零依賴手刻。
- 效能依已知負載、實測瓶頸或明確的可靠性需求決定，不為假設的規模提前優化。已知限制容易被誤用時，才就近註明適用範圍與重評條件；註記不豁免需求、安全及必要驗證。
- 已確認的安全、資料完整性、故障處理與可靠性屬於當前需求，不能用「保持簡單」延後。

## 4. 精準修改

- 最小修改是「最小充分範圍」，不是最少行數。修 bug 要消除本次根因；動到共用邏輯就檢查相關呼叫端，依影響證據擴大範圍，不用局部補丁留著同一缺陷。
- 每處修改都對得上本次需求、必要驗證或本次造成的清理。無關的格式、命名、註解與檔案不順手改；自己造成的未使用程式要清掉；既有的無關問題只在確實重要時簡短提醒。
- 驗證放在信任邊界：外部輸入、權限、第三方回應。內部可信資料不層層重複檢查；型別斷言不算執行時驗證。
- 保留既有 API 契約與業務語意；搬移、合併或簡化時，也保留仍適用的保護與無障礙行為，修正缺陷不必保留原實作。不默默吞錯、不假回成功、不改測試掩蓋錯誤，也不用廣泛 `any` 或忽略型別錯誤來過關——這些只是把問題變得更難查。
- 反覆失敗時先取得新證據（重現、錯誤輸出、最小實驗）再改，不盲目疊補丁、擴張架構或更換依賴。

## 5. 驗證

證據要不依賴新實作的假設：缺陷重現、既有契約、可觀察的整合結果。力度依上表。

- Bug：可行時先寫會因該缺陷而失敗的回歸測試，再修到通過。無法重現或環境不足時說明限制，不宣稱已證明修復。
- 取 TDD 的好處，不強制每個任務跑完整紅綠重構，也不因「先寫了實作」刪掉有效程式；專案明訂 TDD 時照專案。
- 用專案已安裝、版本已固定的工具與 scripts，先確認命令不動到正式環境。從相關的最小集合跑起，跨模組或專案要求時擴大；不只挑容易通過的測試，也不為儀式新增測試框架。
- 高風險且仍有盲點才考慮額外審查；Agent 數、固定覆蓋率或 QA 報告不能取代驗證。
- 交付前看最終 diff：需求完成了嗎、測試真的跑過嗎、有無誤傷既有變更、洩漏密鑰、改多了或留下假成功。

## 6. 回報與授權

- 改好程式不等於可以上線。提交、推送、正式部署、遠端資源變更、資料遷移與刪除，只在使用者明確授權的範圍內做。
- 回報只講：改了什麼、實際的驗證方法或命令、結果與涵蓋範圍、尚存的風險或阻礙。
- 「已實作」「已驗證」「已部署」分開說，各自對得上實際證據；沒跑的測試寫沒跑，局部通過不說成整體通過。
- 必要行為沒驗到時寫出具體缺口與影響。高風險缺口擋住相關的上線與不可逆步驟，不擋其他安全的工作；免責聲明不能代替驗證。
- 需求達成、驗證相稱、沒有阻礙就停，不因「還能更漂亮」加框架、文件、功能或無關重構。

回報範例（長短依任務調整）：

> 已修正優惠碼重複套用：`applyCoupon()` 先檢查訂單既有折扣。
> 已驗證：新增回歸測試（修前失敗、修後通過），`npm test -- coupon` 全過。
> 未驗證：沒有在測試環境實際結帳。未提交、未部署。

## 預設不做

除非使用者明確要求或專案規範需要：

- 不產生 PRD、ADR、Ticket、工作日誌、新規則檔或下一輪待辦；不例行建立或更新交接檔（README／todo／status），也不把這些文件當開工前置。既有的專案說明可按需閱讀。
- 不安裝 MCP、啟動 Sub-agent、建立 Worktree 或呼叫交接類 Skill。
